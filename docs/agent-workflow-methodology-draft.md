# Agent 工作流方法論草案

建立日期：2026-05-26

## 先不放全域的原因

這份草案來自本專案與你提供的課程逐字稿。它目前適合當成方法論草稿，而不是立刻變成全域規則，因為不同任務需要的 agent 數量、資料來源、驗證方式與外部行動風險都不同。

## 核心概念

不要一開始就叫一個大模型「幫我變專家」。比較穩的做法是先拆成多個小能力，再由主 agent 組織它們產出結果。

這套方法可以稱為：

「研究底稿 -> 角色細胞 -> 任務編排 -> 真實使用 -> 回饋優化」

## 工作流

1. 定義任務終點

先說清楚完成條件，而不是只說「幫我優化」。例如：使用者願意開始測驗、能做完、看得懂結果、知道下一步。

2. 先做領域研究

用 web search、官方資料、社群語境、競品頁面與使用者留言整理出使用者真正的關心點。研究不是為了堆資料，而是為了建立判斷標準。

3. 建立 persona 或 power user agent

把研究結果轉成具體角色。角色需要有生活情境、動機、焦慮、常用平台、語言習慣與退出原因。

4. 讓 agent 實際走流程

不是只評論文案，而是像真實使用者一樣從首頁開始，讀 CTA、做題、看結果、判斷是否願意分享或下一步行動。

5. 用 rubric 產出回饋

每次輸出固定包含：
- 興趣判斷
- 會開始的理由
- 可能退出的位置
- 最有共鳴的句子
- 最不清楚的句子
- 一個最值得修改的地方
- 是否需要部署

6. 主 agent 做取捨

不是所有 feedback 都改。主 agent 要判斷哪個修改最能改善使用者理解、信任與行動意圖，並避免讓產品目標被短期回饋牽著走。

7. 修改後驗證

前端類任務至少驗證：
- build 是否通過
- 手機寬度是否沒有橫向溢出
- 關鍵文案是否出現在公開頁面
- 舊文案是否真的消失

## 適合拆出的 agent 類型

- Research Agent: 查資料、整理趨勢、找出使用者語境。
- Persona Agent: 以特定一般民眾、power user 或目標族群角度走完整流程。
- Clarity Agent: 專門挑出看不懂、太專業、太像推銷的句子。
- Layout Agent: 專門看手機閱讀、斷行、視覺密度與掃讀。
- Risk/Compliance Agent: 檢查是否誤導、過度承諾、像投資建議或金融商品推薦。
- Orchestrator Agent: 決定採納哪個建議、實作、驗證與部署。

## 放全域前的條件

可以考慮放全域的部分：
- 先定義完成條件。
- 研究底稿要轉成可測試 persona。
- 回饋要用 rubric 輸出。
- 修改後要有驗證證據。

暫時不應放全域的部分：
- 每次都要大量 web search。
- 每次都要啟動多個 subagent。
- 沒有證據就把 persona 當成真實市場結論。
- 自動部署、外部發布或收集真人資料。
